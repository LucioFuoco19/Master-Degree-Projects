A first problem we notice is given by SQLite with the following error:

[SERVER ERROR to u6_240_54738422]: db error: database is locked
[SERVER ERROR to u6_216_54738422]: db error: database is locked
[SERVER ERROR to u6_5_54738422]: db error: database is locked
[SERVER ERROR to u6_28_54738422]: db error: database is locked
[SERVER ERROR to u6_247_54738422]: db error: database is locked
[SERVER ERROR to u6_5_54738422]: db error: database is locked

The reason: SQLite is a file-based database. By default, it only allows one writer at a time. 
When 250 users try to send messages (write to the DB) at the same time, a queue is created. 
If a thread waits too long to get the "lock" (permission to write), 
SQLite times out and returns the database is locked error.

The Solution (optimization): WAL and Busy Timeout modes
We need to configure SQLite to better manage concurrency. 
We need to enable WAL (Write-Ahead Logging) mode and increase the wait time (busy_timeout).

Changes Made

Changed the SqliteStorage::new function by adding three configurations (PRAGMA) 
Fundamental to SQLite in multi-threaded/multi-process environments:
    - journal_mode = WAL: Enables Write-Ahead Logging. This radically changes the way SQLite handles locks. 
        Instead of locking the entire database for a write, it writes the changes to a separate file. 
        This allows readers and writers to operate simultaneously.
    - busy_timeout = 5000: Sets a wait time of 5 seconds (5000 ms). 
        If the database is occupied by another thread, instead of immediately returning an error, 
        Rust will wait up to 5 seconds for it to clear.
    - synchronous = NORMAL: Optimizes disk write speed when using WAL mode, 
        reducing the number of I/O (fsync) operations required, while still maintaining good data security.
        OPTIMIZED 
            - Problem: You used to get "Incorrect credentials" because the server tried to read 
                the user while SQLite was still caching it, due to "synchronous = NORMAL"
            - Solution: Setting synchronous = FULL in storage.rs ensures that when the server responds "Registered", 
                the data is physically on the disk. The next login finds the data 100%.

A second problem to solve is the accuracy of the Timestamp:

In the storage.rs code this function:

fn now_unix() -> i64 {
    use std::time::{SystemTime, UNIX_EPOCH};
    SystemTime::now().duration_since(UNIX_EPOCH).unwrap().as_secs() as i64
}

Use as_secs() (Seconds). Under stress testing with 250 users, probably 200-300 messages are sent in the same second. 
All these messages will have the exact same timestamp (e.g. 1700001234).
When the query occurs: SELECT... ORDER BY sent_at DESC
If 100 messages have the same time, the database doesn't know which one to put first. 
The order becomes "random" (or based on unpredictable internal details).

The Solution:

To ensure the correct order even under stress, you need to move to milliseconds,
by changing the now_unix function in server/src/storage.rs:

fn now_unix() -> i64 {
    use std::time::{SystemTime, UNIX_EPOCH};
    // Use as_millis() instead of as_secs()
    SystemTime::now().duration_since(UNIX_EPOCH).unwrap().as_millis() as i64
}

In this way:
    - First: 2 messages in the same second -> Sorting conflict.
    - Now: 2 messages must arrive in the same thousandth of a second to have conflict (much rarer).

Stress test code optimization:
    - Ramp-up (Staggered Start): Instead of throwing 'n' connection requests in the same millisecond 
        (which cause a "Thundering Herd" on the server), an imperceptible pause (5ms) is inserted between clients.
    - Smart Retry on Login: With SQLite in synchronous WAL (FULL) mode, there is physical latency between the INSERT (Registration) command 
        and the time when the data is readable for SELECT (Login).
        Instead of crashing immediately, the client "understands" that the server is busy and tries again after 200ms. This absorbs the disk latencies.
        If the server port is saturated momentarily, the client does not give up but retries the TCP connection for up to 10 seconds.
    - Low-frequency monitoring: The sysinfo library must make many calls to the operating system to read CPU and RAM. 
        Doing this every second on a heavy load "steals" time from the processor that is supposed to handle the messages instead.
        Sampling every 3 seconds still provides a valid average but reduces monitoring overhead by 66%.
        Technique: Tokio Worker Threads -> #[tokio::test(flavor = "multi_thread", worker_threads = 32)]
        By increasing the runtime threads to 32, you allow Tokyo to better parallelize the 250 tasks of the 
        client + the server task + the monitoring task, preventing one "heavy" task from blocking the others.
